# 오답 분석 (LLM)

문항별 오답 패턴마다 어떤 개념이 부족했는지, 또는 어떤 실수를 했는지 OpenAI 모델로 추정한다. 입력은 `데이터 전처리/전처리 결과`를 그대로 사용한다.

## 실행

```bash
pip install -r "오답 분석/코드/requirements.txt"
cp .env.example .env        # OPENAI_API_KEY, OPENAI_MODEL 입력

python "오답 분석/코드/analyze_errors.py" --dry-run         # 호출 없이 대상 수·프롬프트 확인
python "오답 분석/코드/analyze_errors.py" --limit 20        # 시험 실행 후 결과 검토
python "오답 분석/코드/analyze_errors.py"                   # 전체 실행. 중단돼도 재실행하면 이어서 진행
python "오답 분석/코드/analyze_errors.py" --items 40769390  # 특정 문항만
python -m unittest discover -s "오답 분석/코드" -p "test_*.py" -v
```

## 모델 비교 (전체 실행 전)

```bash
python "오답 분석/코드/benchmark_models.py" --dry-run   # 비교 문항 10개와 선정 이유 확인
python "오답 분석/코드/benchmark_models.py"             # .env의 BENCHMARK_MODELS로 실행
```

- 모든 모델이 같은 10문항을 분석한다. 선정 기준: 해설 없음, 재채점상 정답 포함, 품질 표시, 오답 패턴 6개 이상, 무순형, 이미지 각 1개 이상 + 문항형태·지식을 고르게. 고정 seed라 매번 같은 문항이 뽑힌다.
- 비용은 실제 사용 토큰(입력·캐시 입력·출력, 출력에 추론 토큰 포함)에 `코드/model_prices.json`의 가격을 곱한다. 검증에 실패한 시도의 토큰도 합산한다.
- 결과는 `분석 결과/모델 비교/<시각>/`에 저장된다.

| 파일 | 내용 |
|---|---|
| **`모델 비교 결과.xlsx`** | `오답 판단` 시트: 문항별 오답(선지·응답) 1행에 모델별 판단(유형·신뢰도·부족 개념·오개념)과 근거(추정 풀이). `비용` 시트: 모델별 토큰·총비용·문항당·전체 실행 예상, 문항×모델 비용표 |
| `모델별 비용·성능 요약.csv` | 비용(합계·문항당·패턴당·전체 실행 예상), 지연, 첫 시도 통과율, 판단 불가·낮은 신뢰도 비율 |
| `오답 패턴별 모델 비교_검수표.csv` | 오답 패턴 1행에 모델별 유형·개념·오개념·추정 풀이를 나란히. 점수(1~5)·최선 모델·메모 칸은 사람이 채운다 |
| `풀이 단계 비교.csv` | 모델별 풀이 단계와 출처(해설/보완/생성) |
| `모델별 문항 실행 기록.csv` | (모델, 문항)별 토큰·비용·시도 횟수·오류 |
| `모델 비교 결과.json` | 위 요약과 모델 간 오류 유형 일치율 |

정답 라벨이 없으므로 성능은 자동으로 판정하지 않는다. 자동 지표(판단 불가 비율, 모델 간 일치율 등)는 참고용이고, 검수표의 사람 점수로 판단한다.

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 분석 단위 | 문항 1개 = API 호출 1회. 그 안의 서로 다른 오답 패턴을 한꺼번에 분석 | 같은 문항의 오답끼리 비교해야 원인을 구분할 수 있고, 문항 본문을 한 번만 보내면 된다 |
| 오답 정의 | 원본 `source_correctness=N` | 패킷의 오답 분포와 같은 기준이다. 재채점 결과(`regraded_result_counts`)는 함께 전달해, 정답일 가능성이 있는 34건은 `possibly_correct`로 분류되게 했다 |
| 전부 미응답인 패턴 | LLM에 보내지 않고 `no_response`로 규칙 처리 | 응답이 없으면 원인을 추정할 근거도 없다 |
| 제외 문항 | `blocked_source_defect`, `unresolved` (오답 17건) | 기준 정답이 확정되지 않았다 |
| 내용 검토 필요 문항 | 분석은 하되 품질 표시를 함께 전달하고 `item_quality_note`에 기록 | 판단은 분석 단계에서 한다는 전처리 원칙을 따랐다 |
| 풀이 단계 | 해설(텍스트 또는 해설 이미지 설명)이 있는 2,093문항은 해설의 풀이 흐름을 따라 단계로 나누고, 없는 104문항만 직접 작성. `step_source`로 출처를 기록하고 규칙 위반 시 재시도 | 오답 위치(`wrong_step`)를 공식 해설 기준으로 맞춘다 |
| 오류 유형 | 9개로 고정(아래 표) | 군집화·집계에 쓰려면 고정된 값이어야 한다 |
| 개념 | 문항마다 `required_concepts`(C1, C2…)를 먼저 정의하고 각 오답에서 ID로 참조 | 공식 개념 체계가 없다. 문항 밖에서 개념 이름을 맞추는 작업은 후속 단계에서 한다 |
| 출력 형식 | Structured Outputs(json_schema, strict) + 코드 검증(모든 패턴 포함 여부, 개념 ID, 단계 번호). 실패하면 재시도 | 응답 파싱 실패와 패턴 누락을 막는다 |
| 이미지 | `CHUNJAE_RAW_ROOT`가 지정되면 중1-1 PNG를 첨부 | 그림이 필요한 문항이 있다. PNG에 정답이 포함되어 있지만, 분석에는 어차피 정답을 제공한다 |
| 데이터 보호 | 학생 ID는 보내지 않음. `store=false` | 기업 제공 데이터다 |
| 캐시·재개 | 프롬프트 버전·모델·입력의 해시가 같고 이미 성공한 문항은 건너뜀 | 중간 실패에 대비하고 비용 중복을 막는다 |

### 오류 유형 (`error_category`)

| 값 | 뜻 |
|---|---|
| `concept_gap` | 개념 결손 |
| `misconception` | 오개념(잘못된 규칙을 일관되게 적용) |
| `procedural_error` | 절차 오류(방법은 맞고 절차를 체계적으로 틀림) |
| `careless_slip` | 단순 실수 |
| `misread_question` | 문제 해석 오류 |
| `answer_format_error` | 입력 형식·칸 순서 오류 |
| `non_meaningful` | 무의미 응답 |
| `possibly_correct` | 정답 가능성·채점 문제 |
| `indeterminate` | 판단 불가 |
| `no_response` | (규칙) 전체 미응답 |

## 출력 (`분석 결과/`)

| 파일 | 내용 |
|---|---|
| `문항별 오답분석_LLM응답.jsonl` | 문항별 원본 응답·토큰 사용량·캐시 키. 이 파일이 원천 자료다 |
| `오답 패턴별_원인 분석.csv` | 오답 패턴 1행. 응답·칸별 채점·건수·오류 유형·개념·추정 풀이 경로·신뢰도 |
| `문항별_필요 개념.csv` | 문항별 필요 개념(선행 개념 여부 포함) |
| `오답 분석_실행 요약.json` | 대상 수, 실패 문항, 오류 유형별 응답 건수 |

## 주의

- LLM의 추정은 가설이다. 응답 1건만으로는 단순 실수와 개념 결손을 구분하기 어렵다. 실제 판단에는 `confidence`, `attempt_count`, 학생의 다른 문항 이력을 함께 본다.
- 프롬프트나 오류 유형을 바꾸면 `PROMPT_VERSION`을 올린다. 그러면 캐시가 무효화되어 전체 문항이 다시 호출된다.
- 처음에는 `--limit 20`으로 돌려 결과를 사람이 검토한 뒤 전체를 실행한다.
